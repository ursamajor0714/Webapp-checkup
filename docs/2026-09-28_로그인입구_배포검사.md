# 2026-09-28 — 로그인 입구가 여러 개인 앱 · 배포 주소 검사

## 결론

1. **비밀번호 칸 헷갈림 해결.** ⚙ 설정의 비밀번호 칸은 이제 **"관리자 비밀번호 — POST /api/admin/login"** 처럼 어느 입구의 것인지 적힌다.
   관리자 비밀번호는 레포 `.env` 에서 알아서 읽으므로 **비워 둬도 된다.** 저장된 값이 `.env` 와 다르면 빨간 안내와 [저장된 값 지우기]가 뜬다.
2. **회원(홈) 비밀번호는 안 넣어도 된다.** QA 가 코드에서 계정 얻는 길을 찾아 스스로 회원 계정을 만든다.
   크로스핏은 "관리자가 `POST /api/members` 로 회원을 만들고, 기본 비밀번호는 전화번호 뒷 4자리" 라는 걸 코드에서 읽어 회원 2명을 만들어 로그인하고, 끝나면 지운다.
   자동으로 못 만드는 앱일 때만 설정에 **그 입구의 칸**이 뜬다.
3. **회원 쪽 권한 검사가 새로 돈다** — 회원 A 가 회원 B 의 id 로 부르면 막히나(IDOR), 회원 토큰으로 관리자 기능이 막히나.
   일부러 구멍을 심은 시험 앱에서 **두 구멍을 모두 잡았고**, 크로스핏은 **58개 모두 통과**(회원 경로 4개·관리자 경로 29개가 회원 토큰을 막는다).
4. **배포 주소 검사 `--live` 완성 (로드맵 3번).** `node run.js [레포] --live=https://주소` — **읽기만 한다** (GET·HEAD, 로그인·쓰기 없음, 최대 200번).
   주소 제한은 두지 않았다. 크로스핏 로컬 서버로 돌려 **89개 통과 · 문제 0**, 심은 구멍 8개짜리 시험 서버에서 **8개 모두 잡음**.
5. 테스트 **38개 전부 통과** (새 테스트 4개 포함).

## 1. 로그인 입구 여러 개 — 무엇을 바꿨나

### 문제
- QA 는 로그인 입구를 **하나**만 알았다. 크로스핏에는 셋이 있다: 관리자(`/api/admin/login`), 계약서 직원(`/api/contract/login`), 회원(`/api/member/login`).
- 설정 화면엔 "검사용 계정" 칸 하나라 **어느 비밀번호를 넣어야 하는지** 알 수 없었다. 0000 을 넣으면 실패했다.
- 회원 쪽은 로그인한 상태로 한 번도 검사되지 않았다 — "회원끼리 남의 정보를 보나"는 아예 안 봤다.

### 한 것
| 파일 | 내용 |
|---|---|
| `common/roles.js` (새 파일) | 다른 로그인 입구를 찾고, 계정 얻는 길을 코드에서 찾는다: **가입 경로** / **관리자가 만드는 기능** (+ 기본 비밀번호 규칙) / **공용 비밀번호** / 못 찾음 |
| `common/runner.js` | 주 로그인 뒤 다른 입구 계정을 준비. 만든 계정은 기존 "검사가 만든 것" 기록에 올라가 끝나면 지워진다. 못 들어간 입구는 점수 밖 안내로 |
| `common/areas/security/c_authorization.js` | 회원끼리 IDOR · 회원 토큰으로 관리자 기능 — 두 검사 추가 |
| `ui.js`, `common/ui/index.html` | 설정 화면: 비밀번호 칸에 입구 이름, `.env` 와 다르면 경고 + 지우기, "다른 로그인 입구" 목록 (자동이면 "넣을 것 없음", 아니면 칸) |

### 하다가 찾아 고친 것 (기존 오탐 2개 포함)
| 무엇 | 원인 | 고침 |
|---|---|---|
| 관리자로 들어간 계정을 "일반 계정"으로 보고 `GET /api/admin/me` 가 열린다고 문제로 잡음 **(기존 오탐)** | `ownerIsAdmin` 을 쓰는 곳은 있는데 **정하는 곳이 없었다** | 로그인 경로가 admin 이거나 비교 대상이 ADMIN_PASSWORD 면 관리자로 본다 |
| `GET /admin` (누구에게나 같은 화면 틀)을 "회원이 관리자 기능을 쓴다"로 잡음 **(기존 오탐)** | 화면 HTML 과 데이터를 구분 안 함 | 로그인 없이 부른 것과 **똑같은 HTML** 이면 화면 틀로 보고 통과 (데이터는 API 가 막는지로 본다) |
| 계약서 입구 로그인이 틀린 비밀번호로 시도됨 | 설정에 저장된 틀린 값을 썼다 | 관리자 로그인이 **실제로 통한** 비밀번호를 쓴다 |
| 뒷정리가 "4개 중 3개 지움"으로 나옴 | 검사용 데이터 정리가 먼저 지운 것을 한 번 더 지우려다 404 | 404 는 "이미 없음"으로 센다 |
| 설정 화면에서 비밀번호 칸이 반쪽 폭 | 아이디 칸을 숨겨도 두 칸 격자 그대로 | 비밀번호만 쓰는 앱은 한 칸 폭 |

## 2. 배포 주소 검사 `--live`

```
node run.js crossfit-grove --live=https://배포주소     # 레포와 같이 — 코드 기준으로 더 본다
node run.js --live=https://아무주소                    # 레포 없이 — 주소만으로 볼 수 있는 것만
node run.js crossfit-grove --live                      # 설정의 liveUrl 을 쓴다
```

**지키는 것** — GET·HEAD 만 (한 함수에서 강제, 다른 메서드는 예외를 던진다) · 한 번에 하나씩 쉬면서 · 최대 200번(`QA_LIVE_MAX`) ·
로그인·쓰기·무차별 대입·퍼징 없음 · **주소 제한 없음** (허락받은 남의 사이트도 돌린다는 결정대로).

| 주소만으로 보는 것 | 레포를 주면 더 보는 것 |
|---|---|
| 첫 화면·응답 속도, http→https, 인증서 남은 날, HSTS | 코드엔 로그인 가드가 있는 GET API 가 배포본에서도 막히나 (옛 코드가 떠 있나) |
| 보안 헤더 5종, 서버 종류 노출 | 코드에 있는 화면이 배포본에서 열리나 |
| `/.env`·`/.git`·백업 SQL·Spring actuator 등 11개, 소스맵(.map) | public·static 의 js·css 가 레포와 같나 (옛 파일이 떠 있나) |
| 없는 주소의 오류 화면에 스택·경로, CORS 가 아무 사이트에 쿠키 허락 | 설정의 `removedRoutes` 가 정말 없나 |

크로스핏 전용이던 `projects/crossfit-grove/check-live.js` 가 하던 일(화면·파일 대조·지운 API·인증 없이 접근·헤더·https)을 전부 범용으로 옮겼다.
그 파일은 지우지 않고 남겨 뒀다 (지울지는 사용자가 정한다).

### 검증
| 대상 | 결과 |
|---|---|
| 시험 서버 (단위 테스트 — "옛 코드가 떠 있는 배포본" 흉내) | `.env` 노출 · 서버 종류 노출 · CSP 없음 · 오류 화면 스택 · CORS 되돌림+쿠키 · 가드 빠진 API · 옛 app.js · 소스맵 — **전부 잡음**. 가드 있는 API·같은 css 는 통과. **보낸 요청이 모두 GET·HEAD 인지**도 확인 |

|---|---|---|

### 크로스핏 쪽 진짜 문제 (참고 — 고치지 않았다)
- `POST /api/members/:id/messages` 에 글이 아닌 값(숫자 등)을 보내면 `(req.body.content || "").trim is not a function` 으로 서버 오류가 난다 (`backend/routes/messages.js:20`).
  `typeof content === 'string'` 확인을 먼저 하면 된다.
- 빈 값으로 공지·가격표·운동복을 만들면 DB 의 "비어 있으면 안 됨" 규칙에 걸려 오류가 로그에 남는다 (입력 검사가 DB 보다 먼저 막아야 한다).

## 4. 확인 못 한 것 · 알게 된 한계

- **https 경로(http→https 이동·HSTS·인증서 경고)는 실제 운영 주소로 돌려 보지 않았다.** 운영 서버에는 QA 를 돌리지 않는다는 원칙 때문. 직접 한 번:
  `node run.js crossfit-grove --live` (읽기만 한다)
- **같은 포트에 다른 앱이 떠 있으면 QA 가 그 앱을 검사한다.** 테스트 중 크로스핏이 3000 번에 떠 있어서 시험 앱 대신 크로스핏에 로그인을 시도했다
  (관리자 로그인 실패 1회가 크로스핏 로컬에 남음 — 10분 뒤 풀림).
  "떠 있는 서버가 이 레포인가" 확인 장치는 이미 있다(코드의 GET 경로를 불러 전부 없는 경로처럼 답하면 다른 서버로 본다).
  이번엔 시험 앱과 크로스핏이 **둘 다 `/api/members` 를 가져서** 통과해 버렸다. 로그인이 실패해 "설정 오류"로 멈췄으므로 크로스핏 데이터는 건드리지 않았다.
  QA 를 돌릴 때 같은 포트에 다른 앱을 켜 두지 않는 것이 가장 확실하다.
- 계정 얻는 길 찾기는 흔한 모양만 안다: SQL `INSERT INTO`·Prisma·Mongoose, 기본 비밀번호는 "전화번호 뒷 4자리" 규칙만.
  다른 규칙(생일 6자리 등)이면 설정 칸이 뜬다.
- 회원 쪽 쓰기 IDOR 는 **검사용으로 만든 회원 B** 에게만 한다 — 진짜 회원 데이터는 건드리지 않는다.
- 관리자 기능 검사는 **관리자 가드가 코드에 붙은 경로**만 본다. 가드를 아예 안 붙인 경로는 기존 "로그인 없이" 검사가 잡는다.
