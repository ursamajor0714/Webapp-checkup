## 추가할 QA 항목 (우선순위순)

### P0: 바로 고쳐야 할 것
1. **클린 설치하면 빌드가 실패합니다.** `zustand`가 package.json에 없어서 `npm ci` 뒤 `next build`가 "Module not found"로 멈춥니다. `@types/d3-selection`, `@types/d3-zoom`도 없어서 tsc가 실패합니다. 세 개를 임시로 깔면 tsc와 빌드 모두 통과합니다.
2. **119 승인이 서버 전체에 한꺼번에 적용됩니다.** 승인이 전역 변수(`app/api/emergency/route.ts:5`) 하나에 저장되어, 한 단말이 OTP를 통과하면 인증하지 않은 모든 단말이 `approved:true`를 받습니다. 만료 시간도 없습니다.
3. **재실자 322명의 위치가 OTP 없이도 브라우저로 내려갑니다.** `types/floor.ts`의 좌표와 호실이 JS 번들(`/_next/static/chunks/…`)에 그대로 들어 있습니다. 화면에서 그리지만 않을 뿐이라 개발자도구로 누구나 볼 수 있습니다.
4. **OTP를 무차별로 시도할 수 있습니다.** `119119`가 코드와 화면에 박혀 있고, 틀렸을 때 응답 메시지에 정답이 나옵니다. 횟수 제한도 없어서 300번 시도가 1.4초에 끝났습니다.
5. **어떤 API에도 인증이 없는데 CORS는 `*`입니다.** 그래서 아무 웹사이트나 방문자 브라우저를 통해 센서를 지우거나 경보를 조작할 수 있습니다. 상황 종료(REVOKE)도 누구나 호출할 수 있습니다.

### P1: 기능 결함
6. **다른 단말에서 지운 센서가 안 사라집니다.** `loadNodes`(`store/useSensorStore.ts:31`)가 서버에 없는 로컬 노드를 계속 붙잡고 있습니다. 실제 스토어 코드를 돌려 재현했고, 그 센서가 ALARM이면 경보음이 멈추지 않습니다.
7. **서버가 저장을 거절해도 화면은 저장된 것처럼 보입니다.** 서버 호출 결과를 `.catch(() => {})` 6곳에서 버리고, 응답 성공 여부(`res.ok`)도 확인하지 않습니다.
8. **입력 검증이 없습니다.** 15개 시나리오 중 15개가 그대로 저장됐습니다(없는 층, 이상한 type·status, 5MB 이름 등).
   - 특히 숫자 id로 들어간 센서는 DELETE로 **지울 수 없습니다**. QA 도구의 자기 점검이 이 잔여물을 잡아내서 발견했습니다.
9. **POST에 기존 id를 보내면 센서가 통째로 덮어써집니다.** 이름·좌표·화각(fov)이 사라집니다. 없는 센서를 DELETE해도 200이 나옵니다.
10. **깨진 JSON이나 null 본문에 500을 돌려줍니다.** 400이어야 하고, 6건이 해당합니다.
11. **감시 공백이 '정상'으로 보입니다.** 한 층의 센서를 모두 철거해도 층 상태가 NORMAL로 나옵니다.
12. **숫자가 서로 맞지 않습니다.**
    - 서버 `peopleCount`는 하드코딩된 286인데, 화면의 재실자 합계는 322입니다.
    - 없는 층에 등록된 센서는 층별 집계에서 빠집니다.
13. **B2 자동 화면 전환 신호를 화면이 읽지 않습니다.** 서버는 `triggerAutoFloorChange`를 보내지만 화면 코드 어디에서도 쓰지 않습니다. `/api/floors`도 화면에서 호출하는 곳이 없습니다.
14. **화면 시각이 UTC입니다.** CCTV 라이브 시각이 9시간 늦게 찍히고, 점검 이력의 기본 날짜는 한국 시간 새벽 0~9시에 어제로 나옵니다.

### P2: 운영과 문서
15. **보안 헤더가 없습니다.** 필수 헤더 6종이 두 페이지 모두에 없고, `X-Powered-By: Next.js`가 노출됩니다. `middleware.ts`는 Next 16에서 deprecated라 `proxy.ts`로 바꿔야 합니다.
16. **서버를 재시작하면 데이터가 초기화됩니다.** 센서는 이름만 DynamoDB인 인메모리 저장이고, 점검 이력은 브라우저 메모리에만 있습니다. health 경로와 감사 로그도 없습니다.
17. **README와 실제가 다릅니다.**
    - "164개 노드"라고 적혀 있지만 실제는 92개입니다.
    - "21개 구역"이라고 적혀 있지만 FLOOR_LIST는 22개입니다.
    - hls.js를 쓴다고 적혀 있지만 실제로 import하는 곳이 없습니다(`tailwind-merge`도 미사용).
18. **의존성과 린트 상태**
    - `npm audit`: 치명 1, 높음 3

    - test 스크립트가 없습니다.
19. **운영 성숙도가 0/18입니다.** CI, 테스트, 감시 장치가 하나도 없습니다. 그래서 제품 점수 47.8에 최저 계수 0.55가 곱해졌습니다.

## 결론: 공용 QA 도구는 만들 수 있습니다

지금 구조에서 매번 새로 만든 부분의 대부분은 사실 **같은 질문을 스택마다 다시 코딩한 것**이었습니다. 두 도구(Grove `express-ejs`, pyroguard2d `nextjs`)의 검사를 나란히 놓으면 이렇게 나뉩니다.

| 분류 | 비율(대략) | 예 | 공용화 방법 |
|---|---|---|---|
| ① 어느 웹 서비스에나 같은 질문 | 약 40% | 보안 헤더, CORS, 깨진 JSON에 500, 없는 것 404, 본문 크기 상한, 토큰 없이 API 접근, 비밀 노출, 취약점, 페이지·링크 열림, health 경로 | **HTTP로 밖에서 두드리면 됩니다.** 스택과 무관하게 코드 한 벌로 됩니다 |
| ② 데이터 모양만 알면 같은 질문 | 약 20% | 중복 등록 409, 스키마 밖 필드 저장, 말 안 되는 값 거절, 동시 등록, 낙관적 잠금 | 프로젝트마다 **"엔티티 이런 모양" 설정 파일**만 두면 공용 코드가 돌아갑니다 |
| ③ 언어·생태계별 정적 검사 | 약 15% | 타입·린트, 선언 안 한 의존성, UTC 잘라 쓰기, innerHTML 같은 위험 코드 | JS/TS·Python·Java **플러그인 3개**로 대부분 커버됩니다 |
| ④ 그 프로젝트 업무 자체 | 약 25% | Grove 금액·홀딩·환불, pyroguard 119 승인·화재 흐름 | 공용화 불가. **여기만 프로젝트별로 씁니다** |

비율은 두 도구의 검사 항목을 제가 손으로 분류한 대략치입니다.

## 공용 도구의 모양
```
QA/
  core/        러너·점수·성숙도 (지금 common/)
  generic/     ① HTTP 블랙박스 검사
  contract/    ② 엔티티 설정 기반 검사
  plugins/     ③ js-ts · python · java 정적 검사
  targets/     프로젝트별 — qa.yaml(설정) + 업무 검사 몇 개(④)
```
새 프로젝트에 붙일 때는 `qa.yaml`만 쓰면 ①~③이 바로 돕니다.
- `qa.yaml`에 넣을 것: 주소, 로그인 방법, 공개 경로, 엔티티 모양, 민감 필드 이름
- ④는 나중에 필요한 만큼만 추가합니다.

## 핵심 과제: API 경로를 어떻게 찾느냐
| 스택 | 방법 |
|---|---|
| FastAPI, Spring(springdoc), Django(DRF) | 대개 **OpenAPI 명세를 자동으로 내보낼 수 있어서** 경로와 엔티티 모양을 둘 다 얻습니다 |
| Express, Next | 명세가 없어서 둘 중 하나가 필요합니다: ① 지금처럼 소스를 긁는 방식(스택별 몇십 줄), ② 브라우저로 화면을 한 바퀴 돌며 실제 요청을 기록(HAR) |
| 정적 사이트(유니버스) | API가 없으니 ①의 페이지 검사와 ③만 돕니다 |

## 기존 오픈소스로 대체할 수 있는 부분

그래서 "100점"은 **"내가 정한 샘플이 전부 통과"** 라는 뜻이지 "빠짐없이 봤다"는 뜻이 아닙니다. 이 README가 스스로 경계한 "합격률 100%인데 스캔률 10%면 안 본 것"이 모집단 정의 단계에서 숨어 버린 셈입니다.

## 업계는 손으로 쓰지 않고 "생성"합니다
수백·수천 건을 하나씩 코딩하는 게 아니라, **규칙을 정의하면 케이스가 자동으로 만들어지게** 합니다.

| 방법 | 하는 일 | 규모 |
|---|---|---|
| 스키마 기반 퍼징 (Schemathesis 등) | API 명세의 필드 정의로 위 300건 같은 조합을 자동 생성 | 엔드포인트당 수백 건 |
| 동등 분할 + 경계값 | 값 유형을 대표값으로 줄임 | 조합 폭발을 줄이는 기본기 |
| 페어와이즈(pairwise) | 모든 조합 대신 "두 개씩 모든 짝"만 | 수만 건을 수십 건으로 줄이면서 결함 대부분을 잡음 |
| 속성 기반 테스트 | "어떤 값을 넣어도 500은 안 난다" 같은 불변식을 무작위 입력으로 검증 | 실행할 때마다 새 입력 |
| DAST 스캐너 (ZAP·Nuclei) | 알려진 공격 패턴을 템플릿으로 보유 | 규칙 수백~수천 개 |
| 뮤테이션 테스트 | 코드에 일부러 버그를 심어 테스트가 잡는지 확인 | "검사가 쓸모 있나"를 잼 |

## 공용 도구 설계가 이렇게 바뀌어야 합니다
1. **모집단을 표준에서 가져옵니다.** ASVS 요구사항 목록을 모집단으로 두고, 각 항목을 "자동 / 사람 확인 / 해당 없음"으로 표시합니다. 그러면 스캔률이 진짜 의미를 갖습니다(예: "ASVS L1 중 62% 자동 검사").
2. **CRUD는 생성기로 만듭니다.** `엔드포인트 × 필드 × 값 유형 × 인증 상태`를 스키마에서 자동 전개하고, 페어와이즈로 줄여 실행합니다. 프로젝트마다 할 일은 스키마(OpenAPI 또는 설정 파일)만 주는 것입니다.
3. **알려진 공격은 기존 스캐너에 맡깁니다.** ZAP·Nuclei·semgrep 결과를 가져와 점수에 합산하고, 직접 짜는 것은 업무 규칙(④)에 집중합니다.
4. **리포트를 두 층으로 나눕니다.** "표준 대비 커버리지"와 "본 것 중 합격률"을 따로 냅니다.

## 1. 규칙에서 검사를 자동으로 만드는 엔진
**센서 규칙을 한 번 적어 두면**(예: "x는 0~100 숫자", "상태는 4가지 중 하나") 기계가 검사를 만듭니다.
- 이상한 값: 빈값, 범위 밖, 글자 대신 숫자, 너무 긴 값, 해킹 문자열 등
- 여러 칸의 조합, 가짜 로그인 토큰

판정 기준은 세 가지뿐입니다.
- 맞는 값은 저장되고, 다시 읽었을 때 보낸 그대로여야 합니다.
- 틀린 값은 거절되고, 아무것도 바뀌지 않아야 합니다.
- 서버 오류(5xx)는 어떤 경우든 문제입니다.

| | 손으로 고른 검사 | 자동 생성 |
|---|---|---|
| 검사 수 | 15개 | 약 590개 |
| 고치기 전 버전에서 잡은 문제 | 15개 | 204개 |

손으로 고른 검사는 "입력 검증이 없다" 정도만 알려 줬습니다. 자동 생성은 문제를 종류별로 나눠 보여 줍니다.
- 틀린 값을 받아들임: 178건
- 서버 오류: 3건
- 저장해 놓고 지울 수도 없는 데이터: 3건
- 로그인 없이 통과: 18건

**새 결함도 하나 찾았습니다.** "전원 꺼진 비상문은 잠글 수 없다" 규칙이 수정할 때만 지켜지고, 새로 등록할 때는 빠져 있었습니다. 제가 지난번에 놓친 부분이라 pyroguard에서 고쳐 두었습니다.
