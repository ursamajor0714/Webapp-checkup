# QA — 웹 서비스 품질 측정

만든 것을 **재는 도구**다. "다 됐습니다" 대신 "26개 영역 중 무엇을 몇 개 보았고, 그중 몇 개가
멀쩡했는지" 를 숫자로 낸다.

```
node express-ejs/run.js                 전체 (단일 A~Z + 복합)
node express-ejs/run.js --single        단일 영역만 (복합 W·X·Y 제외)
node express-ejs/run.js --only=c,m,x    일부만
node express-ejs/run.js --json          결과를 JSON 으로

node express-ejs/check-staged.js        커밋 직전 — 올리려는 것에 비밀이 섞였는지 (서버 없어도 됨)
node express-ejs/check-live.js          배포 뒤 — 올린 것이 실제로 반영됐는지 (읽기 전용)
```

측정 대상은 `qa.config.js` 에서 바꾼다. 지금은 CrossFit Grove 관리 시스템을 가리킨다.
**대상 서버가 떠 있어야 한다** — 코드만 읽는 게 아니라 실제로 API 를 두드려 보기 때문이다.

## 1. 무엇을 재는가 — 스캔률과 합격률은 다르다

이 둘을 섞으면 숫자가 거짓말을 한다.

| 용어 | 뜻 | 계산 |
|---|---|---|
| **모집단** | 그 영역에서 검사할 수 있는 대상 전체 | 예: 서버가 가진 API 경로 전부, 화면이 참조하는 DOM id 전부 |
| **스캔** | 그중 이번 실행이 실제로 들여다본 수 | |
| **스캔률** | 얼마나 **넓게** 봤나 | 스캔 ÷ 모집단 |
| **합격** | 들여다본 것 중 문제가 없던 수 | |
| **합격률** | 본 것 중 얼마나 **멀쩡한가** | 합격 ÷ (스캔 − 확인필요) |
| **확인 필요** | 기계가 확신할 수 없어 사람이 봐야 하는 것 | 점수에 반영하지 않는다 |

스캔률 100% 인데 합격률 50% 면 나쁜 제품이고, 합격률 100% 인데 스캔률 10% 면 그냥 안 본 것이다.
**둘 다 내야 말이 된다.**

`확인 필요` 를 따로 둔 이유는 정직성 때문이다. 예를 들어 "화면에 값을 넣을 때 escape 했는가" 는
변수 이름만 보고 판단하므로 기계가 확정할 수 없다. 이런 것을 불합격으로 세면 점수가 부풀거나
깎이고, 무엇보다 **진짜 결함이 소음에 묻힌다.**

### 최종 점수 — 두 축을 곱한다

```
제품 점수 = Σ(영역 가중치 × 영역 합격률) ÷ Σ(가중치) × √스캔률 × 100
최종 점수 = 제품 점수 × 운영 성숙도 계수
```

**왜 두 축인가.** 합격률만으로는 대기업과 1인 개발을 구분할 수 없다. 둘 다 오늘 검사하면
통과할 수 있다. 차이는 **내일 누가 먼저 발견하느냐** 다. 아래에서 100 을 "CI·자동 검사·감시가
있는 상태" 로 정의했으니, 그런 장치가 없는데 100 이 나오면 정의와 점수가 어긋난다.

- **제품 점수** — 지금 이 순간 멀쩡한가 (A~Z 26개 영역)
- **운영 성숙도 계수** — 멀쩡함이 유지되는 장치가 있는가 (`../common/maturity.js`, 10개 항목 18점)

성숙도 계수는 **0.55 ~ 1.00** 이다. 0점이어도 0.55 아래로는 안 깎는다. 자동화가 없다는 것은
**'나빠질 위험'이지 '이미 나쁨'이 아니기** 때문이다.

스캔률을 그대로 곱하지 않고 제곱근을 쓰는 이유: 모집단이 큰 영역(화면 연결은 대상이 1000개가 넘는다)
하나 때문에 전체가 과하게 깎이는 것을 막는다. 덜 본 만큼은 깎되, 비례해서 깎지는 않는다.

가중치는 **틀렸을 때 사장님이 입는 피해** 순서다. 돈이 틀리는 것(M·X·Y)과 정보가 새는
것(C·I·K·P)이 가장 무겁고, 문구(U)나 로그(L)는 가볍다.

### 운영 성숙도 10개 항목 (18점)

| 점 | 항목 |
|---|---|
| 3 | 배포할 때마다 자동으로 검사가 돈다 (CI) |
| 3 | 레포 안에 자동 테스트가 있다 |
| 2 | 이 QA 같은 회귀 검사 도구가 붙어 있다 |
| 2 | 장애를 사람보다 먼저 알려 주는 감시가 있다 |
| 2 | 운영과 분리된 시험 환경이 있다 |
| 2 | DB 백업·복구 절차가 있다 |
| 1 | 결정과 작업 내용이 문서로 남는다 |
| 1 | 배포 절차가 코드로 적혀 있다 |
| 1 | 의존성 취약점을 정기적으로 본다 |
| 1 | 배포를 되돌리는 방법이 적혀 있다 |

## 2. A~Z 26개 영역

각 영역은 `front/`·`front-api/`·`api/`·`security/` 네 칸 중 한 곳의 파일 하나다. 단일로도 돌고, 전체로도 돈다.

| | 영역 | 무엇을 보는가 | 가중치 |
|---|---|---|---|
| A | API 계약 | 화면이 부르는 경로가 서버에 있는가, 죽은 API 가 있는가 | 5 |
| B | 인증 | 로그인 없이 보호된 API 에 닿는가 | 6 |
| C | 권한 | 코치가 허락받지 않은 곳을 보는가 (단일·복합) | 7 |
| D | 데이터 무결성 | 보낸 값이 그대로 저장되는가, 트랜잭션을 쓰는가 | 6 |
| E | 에러 처리 | 잘못된 요청에 500 이 아니라 4xx 로 답하는가 | 5 |
| F | 입력 검증 | 말이 안 되는 값을 서버가 거절하는가 | 6 |
| G | 화면 연결 | 스크립트가 찾는 칸이 있는가, 버튼이 부르는 함수가 있는가 | 6 |
| H | 보안 헤더 | CSP·HSTS·쿠키 설정이 붙는가 | 4 |
| I | 주입 | XSS·SQL 주입이 통하는가 | 7 |
| J | 응답 규격 | 서버가 주는 모양과 화면이 기대하는 모양이 같은가 | 5 |
| K | 비밀 노출 | 비밀번호·키가 코드나 응답에 섞여 나가는가 | 7 |
| L | 로깅 | 문제가 났을 때 알 방법이 있는가 | 3 |
| M | 금액 계산 | 돈이 맞는가 (DB 원본과 대조) | 8 |
| N | 탐색 | 화면 사이 길이 끊기지 않았는가 | 4 |
| O | 응답 크기·속도 | 데이터가 늘면 터지는가 | 5 |
| P | 개인정보 | 필요 없는 사람에게 필요 없는 정보가 가는가 | 6 |
| Q | 쿼리 효율 | 한 번에 될 일을 N 번 하는가, 인덱스가 있는가 | 4 |
| R | 동시성 | 같은 순간 두 번 눌렀을 때 두 번 처리되는가 | 6 |
| S | 상태 전이 | 등록→홀딩→환불에서 숫자가 따라오는가 | 6 |
| T | 시간·날짜 | 한국 시간, 말일, 윤년, 달 경계 | 5 |
| U | 화면 문구 | 사용자가 읽는 글이 말이 되는가 | 3 |
| V | 의존성 | 남의 코드가 안전한가, 쓰지도 않는 것을 깔았는가 | 3 |
| W | 업무 흐름 | 실제로 하는 일을 처음부터 끝까지 (**복합**) | 8 |
| X | 기능 간섭 | 여러 기능을 뒤섞었을 때 서로를 망가뜨리는가 (**복합**) | 9 |
| Y | 숫자 일관성 | 같은 것을 여러 화면이 같은 값으로 말하는가 (**복합**) | 7 |
| Z | 빈 상태·경계값 | 아무것도 없을 때, 극단값일 때 | 4 |

### 단일 QA 와 복합 QA

- **단일**: 영역 하나만 본다. "권한 키를 하나만 줬을 때 그 곳만 열리는가" 같은 것.
- **복합(W·X·Y)**: 여러 기능을 엮는다. "회원 등록 + 락커 배정 + 가계부 입력 + 환불을 한꺼번에
  하고, 달별 합계를 SQL 로 따로 계산해 대조한다" 같은 것.

**실무에서 사고는 거의 복합에서 난다.** 기능 하나씩은 다 통과하는데 같이 쓰면 숫자가 어긋난다.
그래서 X 의 가중치가 가장 높다.

## 3. 등급 — 대기업을 100 으로 놓았을 때

100 을 무엇으로 잡았는지부터 밝힌다. 그래야 60 이 무슨 뜻인지 말이 된다.

**여기서 '대기업 수준(100)' 은 아래를 전부 갖춘 상태다.**

- 26개 영역 전부에 자동 검사가 있고, **배포할 때마다 CI 에서 자동으로 돈다**
- 취약점 점검·부하 시험·접근성 점검이 **별도 조직에서 정기적으로** 돈다
- 장애를 사람이 발견하기 전에 **감시 시스템이 먼저 알린다**
- 개인정보 처리 방침·보관 기한·감사 로그가 **법적 기준에 맞춰 관리된다**

즉 100 은 "버그가 없다" 가 아니라 **"빠뜨릴 구조가 아니다"** 이다.
버그는 어디에나 있다. 차이는 그것을 **누가 먼저 발견하느냐** 다.

| 구간 | 점수 | 어떤 상태인가 |
|---|---|---|
| **대기업** | 90 ~ 100 | 네이버·카카오·토스 같은 곳의 서비스. 전담 QA 조직과 CI 가 있다. |
| **중급 상위** | 75 ~ 89 | 돈·권한·개인정보처럼 아픈 곳은 자동 검사로 지킨다. 감시와 부하 시험이 없다. |
| **중급** | 60 ~ 74 | 주요 흐름은 돌고 큰 구멍은 없다. 검사는 사람이 기억해서 돌린다. |
| **초급 상위** | 45 ~ 59 | 기능은 다 되지만 검사가 눈으로 하는 수준. 고치면 다른 데가 깨지는지 모른다. |
| **초급** | 30 ~ 44 | 만든 사람만 쓸 수 있는 상태. 돈이나 권한이 틀려도 한참 뒤에 안다. |
| **미완성** | 0 ~ 29 | 주요 흐름이 끊겨 있다. |

### 수준별 기대 점수대 (최고 / 최저)

| 수준 | 최저 | 최고 | 설명 |
|---|---|---|---|
| 대기업 | 90 | 100 | 전담 QA · CI · 상시 감시 |
| **중급** | **60** | **89** | 개발자 몇 명이 붙은 스타트업·중소기업 제품. 아픈 곳만 자동 검사. |
| **초급** | **30** | **59** | 1인 개발 · 외주 납품 직후. 기능은 되지만 회귀 검사가 없다. |
| 미완성 | 0 | 29 | 개발 중이거나 주요 흐름이 끊긴 상태 |

구간을 이렇게 나눈 근거:

- **60 이 중급의 바닥인 이유** — 26개 영역 중 절반 남짓을 통과한다는 뜻이다. 돈·인증·권한처럼
  가중치가 큰 영역이 무너지면 이 아래로 떨어진다. 즉 **60 미만은 "돈이나 정보가 새고 있을 수 있다"** 는 신호다.
- **90 이 대기업의 바닥인 이유** — 26개 영역에서 평균 90% 이상을 통과하려면, 사람이 기억해서
  돌리는 검사로는 불가능하다. 자동화가 없으면 이 점수가 안 나온다.
- **30 미만을 미완성으로 본 이유** — 주요 흐름(W)이나 기능 간섭(X)이 통째로 실패하면
  가중치가 커서 이 아래로 떨어진다. 그건 품질 문제가 아니라 아직 안 만들어진 것이다.

## 4. 이 도구의 한계 — 미리 밝혀 둔다

측정 도구는 **자기가 못 재는 것을 말해야** 믿을 수 있다.

- **브라우저에서 실제로 클릭해 본 것이 아니다.** 화면 연결(G)은 소스를 대조하고, 동작은
  가짜 DOM 으로 확인한다. 눈으로 봐야 아는 것(줄바꿈, 색, 반응형)은 못 잡는다.
- **부하 시험이 아니다.** 응답 크기(O)와 반복 조회 시간은 재지만, 동시 접속 100명은 안 해 봤다.
- **접근성(스크린리더·키보드 조작)을 안 본다.** 별도 영역이 필요하다.
- **`확인 필요` 는 결론이 아니다.** 사람이 봐야 하는 목록이다.
- **모집단은 "코드에서 찾을 수 있는 것" 이다.** 동적으로 만드는 경로처럼 정적으로 안 보이는 것은
  모집단에 안 들어간다. 그래서 스캔률 100% 가 "세상의 모든 것을 봤다" 는 뜻은 아니다.

## 5. 따로 도는 두 가지

### `check-staged.js` — 커밋 직전

`git add` 한 것만 훑어서 비밀이 섞였는지 본다. 서버가 없어도 돌고 1초면 끝난다.

전에 문서 세 곳에 관리자 비밀번호를 평문으로 적어 둔 채 올릴 뻔했다.
**비공개 레포라도 깃 기록에는 지워도 남는다.**

잡는 것: 코드에 박힌 비밀번호, 문서에 적은 비밀번호, API 키, AWS 키, 개인키,
운영 DB 접속 문자열, 문자 발송 키. `localhost` 접속 문자열처럼 밖에서 닿을 수 없는 것은 뺀다.

### `check-live.js` — 배포 뒤

배포한 사이트를 읽기 전용으로 점검한다. **데이터는 건드리지 않는다.**

- 페이지가 전부 열리는가
- **배포된 화면 파일이 레포의 것과 같은가** (옛 파일이 남아 있는지 글자 수로 대조)
- 지운 API 가 정말 404 인가
- 로그인 없이 뚫리는 곳이 없는가
- 보안 헤더가 붙는가

대상 주소는 `qa.config.js` 의 `liveUrl`.

## 6. 도구 자기 점검

`run.js` 를 돌리면 끝에 이 도구 자체도 점검한다. **측정 도구가 거짓으로 실패하면 진짜 결함보다 나쁘다.**
사람이 결과를 안 믿게 되기 때문이다. 실제로 두 번 겪었다.

- 프로브에 `2026-09-20` 같은 날짜를 박아 뒀더니 그날이 지나자 홀딩 검사가 깨졌다 — 제품은 멀쩡한데
- 검사가 만든 회원을 지우면서 락커 이력을 안 치워, 없는 회원의 매출 60,000원을 DB 에 남겼다

그래서 세 가지를 본다.

| 본다 | 왜 |
|---|---|
| 프로브에 '지금 근처' 고정 날짜가 없다 | 날짜가 지나면 검사가 거짓으로 깨진다. `kstDay()` 를 쓴다 |
| 프로브 형식이 맞다 | id·name·weight·run 이 다 있는가 |
| 검사가 만든 데이터를 치웠다 | `QA` 로 시작하는 회원·계약서·가계부가 남았는지, 고아가 생겼는지 |

말일·윤년 계산처럼 **날짜가 고정이어야 의미가 있는** 검사는 그 줄에 `고정날짜` 라고 적어 두면 넘어간다.
의도를 코드에 남겨야 나중에 헷갈리지 않는다.
